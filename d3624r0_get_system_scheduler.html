get_system_scheduler (with concurrent forward progress*)

Abstract

A system context is an execution resource in std::execution that offers concurrent forward progress guarantees. An instance of system_scheduler allows scheduling work on the system context. There is exactly one system context within a program. A system context represents a shared process wide thread pool implementation and/or an interface to an OS-provided system thread pool.

Overview

Win32 and Darwin offer platform supported global system threadpools with the following features:

  1. Post work items for execution.
  2. Schedule a work item to run at a particular time (or after a delay).
  3. Associate an I/O operation with a threadpool, so that the handler processing completion will be executed by the threadpool.
  4. Bulk execution (Darwin only), though a bulk algorithm running over non-post work item results in better performance (due to ability to chunk, inline and vectorize loops of chunks, whereas bulk execution in libdispatch is behind ABI boundary and such optimizations are not easily possible).
  5. Maintain an optimal number of threads processing work items:
    1. If a thread gets blocked, another one is released/created to maintain the desired number of active threads.
    2. The number of active threads is kept proportional to the number of cores.
    3. Guards against thread explosion (when newly created threads get blocked).
    4. Shrinks the number of threadpool threads to zero when not needed.

On Windows and Darwin platforms, optimal of number of threads is attained via cooperation with the operating system. On Linux, Apple's libdispatch library achieve similar characteristics via periodic sampling of the state of threadpool threads by reading /proc/self/task/TID/stat

For C++26, we only offer a system scheduler that supports posting for execution a single or a bulk work items. Implementations are encouraged to expose native_handle() member on a scheduler that would allow adding timer and I/O injections into C++26 threadpool while standardization catches up.

Discussion: Is it truly concurrent (*)?

One question was raised whether a parallel execution context with a very large number of threads (100 x std::hardware_concurrency()) can act like windows or darwin threadpools (or libdispatch on Linux). Yes, it can, but not as efficient. The benefits of elastic threadpools that they dynamically optimize for workload running at the moment, mininizing context switches and the working set of the process. It is true, any elastic threadpool has a limit for maximum amount of threads it can create and thus would violate concurrent forward progress when the limit is reached, but, so is launching a std::thread for every work item. Eventually, we will run out of memory. In practice elastic threadpools behave like concurrent execution context for common workloads and thus is a valuable facility.

Implementation experience

System threadpool has been extensively used on Windows and Darwin platforms (and less so, on Linux, using Apple's libdispatch implementation) we consider their usefulness and production use as proven. Here we offer only a thin interface adapter that exposes system threadpool via sender/receive compatible scheduler API.

33.N.M System scheduler [exec.system.scheduler]

An instance of system_scheduler allows scheduling work on the system context. The system context offers concurrent forward progress guarantee. There is exactly one system context within a program.
Implementation limits: The implementation shall support at least up to 2 * `std::this_thread::hardware_concurrency()` execution agents.

33.N.M.1 execution::get_system_scheduler

  1. Returns: An instance of a system_scheduler class that can be used to schedule work onto the system context.

33.N.M.2 execution::system_scheduler class

  1. system_scheduler is a class that models the scheduler concept and provides access to the system execution context.

  2. Two objects sch1 and sch2 of type system_scheduler always compare equal.

  3. If sch is an object of type system_scheduler, then get_forward_progress_guarantee(sch) returns forward_progress_guarantee::concurrent.

33.N.M.3 Associated types [exec.system.scheduler.types]

  1. Let sch be an expression of type system_context. The expression schedule(sch) has type system-schedule-sender and is not potentially-throwing if sch is not potentially-throwing.

  class system-schedule-sender;

  2. An instance of system-schedule-sender remains valid for the duration of execution of the program.

  3. system-schedule-sender is an exposition-only type that satisfies sender. For any type Env, completion_signatures_of_t<system-schedule-sender, Env> is completion_signatures<set_value_t(), set_error_t(exception_ptr), set_stopped_t()>.

  4. Let sndr be an expression of type system-schedule-sender, let rcvr be an expression such that receiver_of<decltype((rcvr )), CS> is true where CS is the completion_signatures specialization above. Let C be either set_value_t or set_stopped_t. Then:
    - The expression connect(sndr, rcvr) has type system-schedule-sender-opstate<decay_t<decltype((rcvr))>>
    - The expression get_completion_scheduler<C>(get_env(sndr)) is potentially-throwing if and only if sndr is potentially-throwing.

  template<class Rcvr>
  struct system-schedule-sender-opstate;

  5. Let o be a non-const lvalue of type system-schedule-sender-opstate<Rcvr>, and let REC(o) be a non-const lvalue reference to an instance of type Rcvr that was initialized with the expression rcvr passed to the invocation of connect that returned o and o is started. Then:
  - The object to which REC(o) refers remains valid for the lifetime of the object to which o refers.
  - The expression start(o) is equivalent to:
     try {
      submits the operation for an execution to the system context.
     } catch(...) {
       set_error(std::move(REC (o)), current_exception());
     }
  - When an execution agent of the system context selects o for execution, it behaves as if it executes the following:
    if (get_stop_token(REC (o)).stop_requested()) {
      set_stopped(std::move(REC (o)));
    } else {
      set_value(std::move(REC (o)));
    }
